Où vit réellement le joueur ?

Dans les trois options, le Hub ne dessine aucune UI en jeu. Il sélectionne une version installée, fournit les sauvegardes et reçoit « retour au Hub ». Le projet JSON est chargé et interprété par le runtime.

A

Runtime autoritaire + renderer map_player_ui — recommandé

Le runtime possède états, navigation, focus et commandes. map_player_ui ne fait que rendre les snapshots Flutter.

pokemap_hubinstaller · bibliothèque · saves · lancement
→
map_player_uiPokeMapPlayerSessionView · menu A1 · thème · accessibilité
⇄
map_runtimeJSON · Flame · session · input router · services contextuels
+ respecte le sens existant : map_player_ui dépend du runtime, jamais l’inverse
+ aucun widget ou état de session dans le Hub
+ design system joueur réutilisé sans duplication
Nuance : le widget vit physiquement dans map_player_ui, mais son état et ses décisions viennent uniquement du runtime
B

Tout placer directement dans map_runtime

Le package runtime contient Flame, la session et tous les widgets Flutter joueur.

pokemap_hubinstaller · bibliothèque · saves
→
map_runtimeJSON · Flame · session · menu Flutter · thème · services
+ correspond littéralement à « tout vient de map_runtime »
− duplique ou déplace le design system déjà construit dans map_player_ui
− grossit fortement le runtime et mélange moteur, orchestration et présentation produit
− rend map_player_ui presque inutile
C

Nouveau package map_player_shell

Un package de composition dédié assemble map_runtime et map_player_ui ; le Hub ne dépend que de ce shell.

+ frontière produit extrêmement nette
+ Hub minimal et runtime moteur préservé
− nouveau package, nouveaux barrels et plus de plomberie
− complexité prématurée tant qu’il n’existe qu’un player officiel
Règle commune pour Boutique et Centre Pokémon : une interaction de monde déclenche une commande Scene typée (`openShop`, `healParty` ou `openHealCenter`). Le runtime verrouille l’overworld puis publie l’écran Flutter approprié. Ces services ne figurent jamais dans le menu pause.

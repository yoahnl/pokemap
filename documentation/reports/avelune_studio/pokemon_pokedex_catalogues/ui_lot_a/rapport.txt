Résultat
========

L’espace Pokémon de Studio permet de consulter le Pokédex, éditer les cinq
sections d’une espèce, choisir une attaque du catalogue, préparer et appliquer
les imports JSON/externe, associer un PNG avec le contrat existant et consulter
ou synchroniser les attaques. Les listes d’attaques utilisent la langue
principale du profil de jeu : la fixture française affiche notamment
Rugissement, Vampigraine, Abri et Charge. Les pictogrammes vectoriels varient
par type, portent une marque physique/spéciale/statut, renforcent leur dégradé
selon la puissance et montrent une étoile lorsque source=project_custom.
Ce marqueur ne prétend pas qu’une attaque officielle simplement modifiée soit
une création personnelle.

Le lot ne crée ni attaque ni espèce, ne change aucun moteur de combat et ne
télécharge pas les médias lors de l’import externe. Les projets personnels,
dont Le Train de 17h42, n’ont pas été ouverts en écriture. Aucun commentaire
n’a été ajouté au code manuel. Aucun commit, push ou changement Notion.

Défaut reproduit, correction et frontières
===========================================

Avant correction, le vrai hôte refusait custom-learn avec « Référence
custom-learn incohérente ». L’aperçu JSON ignorait alors un compagnon legacy.
Une forme partageant les médias de sa base échouait aussi sur « Référence
bulbasaur incohérente ». Journaux rouges dans logs/avelune-lot-a-legacy-red.log,
logs/avelune-lot-a-json-legacy-red.log et logs/avelune-shared-media-red.log.

La règle retenue conserve trois identités distinctes : espèce propriétaire,
référence depuis la fiche et identifiant déclaré par le compagnon. L’identité
déclarée peut être l’espèce ; pour les compagnons legacy, elle peut être la
référence seulement si celle-ci n’est pas une autre espèce connue. Un média
peut être partagé avec une forme non-base qui déclare explicitement sa base.
Un compagnon réellement étranger reste refusé. Chemins personnalisés et
références optionnelles viennent du manifeste et des refs, jamais du nom
affiché. Le validateur map_core résout ces propriétaires pour la cohérence et
les cycles d’évolution sans réécrire les fichiers à la consultation. La
prévisualisation et la transaction conservent les préimages et refusent un
aperçu périmé ; les tests couvrent les deux sections et la réouverture disque.

Passes indépendantes et critique
================================

Audit / Architecture : contrats et frontières réutilisés ; aucun import
Studio → map_editor. Verdict : conforme sur le lot, MCP live PARTIAL.
Implémentation : identité compagnon qualifiée et dix surfaces raccordées
aux propriétaires existants. Verdict : parcours livré, sans nouveau moteur.
Tests : reproductions rouges puis 30 tests Pokémon et 18 de cohérence verts ;
suite générale Studio verte ; cinq échecs map_core globaux non attribués.
Build / Validation : analyse Studio et build macOS réussis ; aucune
manipulation native de l’application construite n’est revendiquée.
Critique finale : les maquettes donnent une densité et un catalogue plus
riches que la fixture de trois espèces ; la comparaison valide la composition
et les états, pas l’acceptation artistique de Yoahn. Les médias externes ne
sont pas téléchargés, le catalogue MCP live est incomplet, et les cinq
échecs map_core hors périmètre restent à diagnostiquer séparément.

Limites préservées : stats et talents en consultation ; aucune création
d’attaque/espèce ; formes liées sans création de fiche ; conditions
d’évolution stockées sans certification de gameplay ; animations et cris
référencés sans nouveau lecteur ; import externe de JSON métier sans binaires ;
aucune promesse d’atomicité entre réseau et binaires. Un changement du profil
de langue pendant que la session Pokémon est déjà ouverte peut nécessiter de
rouvrir l’espace pour rafraîchir l’index. Les captures et tests ne remplacent
pas une validation visuelle native ni un essai de service distant réel.
